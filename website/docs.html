ForensiQ Documentation Everything you need to install, configure, and extend the tool.

ForensiQ is an open-source network forensics tool that turns raw PCAP capture files into structured threat intelligence reports. You give it a network capture, and it gives you back a complete picture of what happened — which hosts were attacked, what techniques were used, and what you should do about it.

It's built entirely in Python and runs locally. No cloud required, no data leaves your machine.

💡
Who is this for? ForensiQ is designed for security professionals, students, incident responders, and anyone who needs to make sense of a network capture quickly. You don't need deep packet analysis expertise — the tool explains everything in plain English.

What ForensiQ detects

Five threat categories are covered out of the box, all mapped to MITRE ATT&CK:

ThreatMITREWhat it looks like
Port ScanT1046One host contacting many ports on another host in a short window
Brute ForceT1110Repeated failed authentication attempts to the same service
C2 BeaconingT1071Regular check-in traffic to an external IP at consistent intervals
Data ExfiltrationT1020Large outbound data transfers to external destinations
DNS TunnelingT1071.004Unusually long DNS query names hiding data in subdomains

Architecture

ForensiQ is a linear pipeline. Every analysis follows the same six steps in the same order. Nothing is skipped, nothing runs in parallel — this makes it completely predictable and easy to debug.

Each step receives the output of the previous step as its input. If a step fails (say, the PCAP is corrupted), execution stops immediately with a clear error — it never silently continues with bad data.

Step 1 — Validate

core/validator.py checks three things before a single packet is read: the file extension must be .pcap, .pcapng, or .cap; the first 4 bytes must match the PCAP magic number (0xd4c3b2a1 or 0xa1b2c3d4); and the file must be under 500 MB. If anything fails, a ValidationError is raised. On success, it returns a sanitised filename and a SHA-256 hash for chain-of-custody tracking.

Step 2 — Parse

core/parser.py uses Scapy to read the PCAP packet by packet. Each packet is added to a flow dictionary keyed by the 5-tuple src_ip:src_port → dst_ip:dst_port + protocol. This reconstructs bidirectional conversations into Flow objects. DNS queries, HTTP host headers, and TLS SNI values are extracted where present.

Step 3 — Detect

detection/engine.py runs all registered rules against the flow list. Each rule runs inside a try/except wrapper, so a crash in one rule never prevents the others from running. All findings are collected and returned together.

Step 4 — Enrich

enrichment/enricher.py extracts IOCs (IP addresses, domains) from each finding and queries VirusTotal for reputation data. Private IP addresses are skipped. Results are cached in SQLite for 24 hours to avoid hitting API rate limits on repeated analyses.

Step 5 — Explain

ai/explainer.py calls Groq's LLaMA 3.1 model with a structured prompt for each finding. The response is validated by Guardrails before it's attached — if the LLM hedges, hallucinates, or doesn't follow the expected format, the explanation is discarded rather than shown.

Step 6 — Report

output/report.py assembles a 6-page PDF using ReportLab, and AnalysisReport.to_json() serialises everything to a structured JSON file. Both are saved to the outputs/ directory.

Core Data Models

Three dataclasses flow through the entire system, defined in core/models.py.

pythoncore/models.py — simplified
@dataclass
class Flow:
    src_ip: str           # Source IP address
    dst_ip: str           # Destination IP address

    dst_port: int

    bytes_transferred: int
    dns_query: str        # Set if protocol is DNS
    http_host: str        # Set if HTTP Host header found
    tls_sni: str          # Set if TLS SNI found

@dataclass
class Finding:
    rule_name: str

    mitre_tactic: str     # e.g. "Discovery"

    explanation: str      # Populated by AI explainer

Detection Rules

Every rule lives in detection/rules/ and extends BaseRule. Rules are given the full list of parsed flows and return a list of Finding objects. They never modify flows — they only read.

Port Scan Detection T1046 · Discovery

Identifies hosts performing automated reconnaissance by counting how many unique destination ports a single source IP contacts within a 60-second window. When that count exceeds the threshold, ForensiQ flags the source as a scanner. This covers both horizontal scans (one host, many targets) and vertical scans (one target, many ports).

Source IP contacts ≥ 15 unique ports within a 60-second window (configurable)
Evidence includes the full sorted port list, duration, and packet count
File: detection/rules/port_scan.py
Brute Force Detection T1110 · Credential Access

Detects repeated authentication attempts from a single source to the same destination port. Brute force tools like Hydra and Medusa generate many short-lived flows to the same endpoint — a pattern that normal user behavior never produces.

Same source → destination:port pair seen ≥ 20 times within 60 seconds
Each flow has ≤ 3 packets (typical of rejected authentication)
Covers SSH (22), RDP (3389), FTP (21), Telnet (23), SMTP (25)
File: detection/rules/brute_force.py
C2 Beacon Detection T1071 · Command & Control

Looks for implant check-in traffic — the telltale regular heartbeat that malware sends back to its command-and-control server. Real user traffic is bursty and irregular. Malware beacons are systematic. ForensiQ measures the variance in timing between repeated connections to the same external host.

≥ 5 connections to the same destination IP
Interval jitter (standard deviation / mean) below 50% tolerance
Interval between connections between 5 seconds and 1 hour
File: detection/rules/beaconing.py
Data Exfiltration T1020 · Impact

Flags flows where a significant amount of data is transferred to an external (non-RFC1918) IP address. Used to catch both large bulk transfers and sustained low-and-slow exfiltration over time.

Outbound flow transferring ≥ 10 KB to a public IP address (configurable)
Private IPs (10.x, 172.16.x, 192.168.x) are excluded from flagging
Evidence includes exact bytes transferred, destination IP, and throughput
File: detection/rules/exfiltration.py
DNS Tunneling T1071.004 · C2 via DNS

DNS tunneling tools like iodine and dnscat2 encode data into subdomain labels to bypass firewalls that only allow DNS traffic. The result is DNS queries with unusually long names — far longer than any legitimate hostname. ForensiQ flags these by checking query length.

DNS query label exceeds 52 characters in length
Or total query length exceeds 100 characters
Evidence includes the full query string for investigation
File: detection/rules/dns_tunnel.py

Configuration

All thresholds, limits, and API settings live in config.py. You never need to touch individual rule files — change a number here and it applies everywhere.

Environment Variables

API keys are loaded from .env via python-dotenv. None of them are required — the tool runs without them with reduced functionality.

KeyRequiredEffect when missing
VIRUSTOTAL_API_KEY Optional IOC enrichment is skipped. Findings still appear but without VT reputation scores.
GROQ_API_KEY Optional AI explanations are disabled. Reports still contain all evidence — just no plain-English write-up.
OTX_API_KEY Optional AlienVault OTX enrichment is skipped. Not used in the current pipeline version.
LOG_LEVEL Optional Defaults to INFO. Set to DEBUG for verbose packet-level logging.

Detection Thresholds

These are the numbers that control when a rule fires. Raise them to reduce false positives on noisy networks. Lower them to catch subtler attacks.

VariableDefaultWhat it controls
PORT_SCAN_THRESHOLD15Minimum unique ports a host must scan before triggering an alert
PORT_SCAN_WINDOW_SECONDS60Time window for counting port scan activity
BRUTE_FORCE_THRESHOLD20Minimum failed connection attempts to flag brute force
BRUTE_FORCE_WINDOW_SECONDS60Time window for counting brute force attempts
BEACON_MIN_CONNECTIONS5Minimum connections to the same host before checking for beacon pattern
BEACON_INTERVAL_TOLERANCE0.50Maximum allowed timing jitter (50% = very relaxed, catches irregular beacons)
EXFIL_BYTES_THRESHOLD10 240Minimum bytes in a single outbound flow to flag exfiltration (10 KB default)
DNS_TUNNEL_LABEL_LENGTH52Maximum allowed DNS label length before flagging as tunnel

Web Interface

The web interface is built with Flask and plain HTML/CSS/JavaScript. No frontend framework, no build step. Start it with one command and it works in any browser.

bash
python app.py
# → http://localhost:5001

Uploading a file

The landing page shows a drag-and-drop upload zone. You can drag a .pcap or .pcapng file directly from your file manager, or click the zone to open a file picker. Files up to 100 MB are accepted.

Live progress

Once the file is submitted, the page switches to a progress view. Each of the 6 pipeline steps lights up as it completes — validated with a green checkmark, currently running with a spinner, pending in grey. The backend sends these updates over a Server-Sent Events (SSE) stream, so the page updates in real time without polling.

Reading the results

When analysis completes, the results render in-place:

  • Severity summary — a row of chips showing how many findings at each severity level
  • Metrics bar — flows, packets, bytes, finding count, analysis duration
  • Findings accordion — each finding is a collapsible card. Click to expand for the flow diagram, evidence table, port heatmap, AI explanation, and IOC list
  • IOC table — deduplicated list of all indicators with VirusTotal scores
  • Download buttons — PDF report and raw JSON

API Reference

The Flask server exposes four endpoints. All are used internally by the web interface, but you can call them directly from scripts or other tools.

POST /analyze Submit a PCAP for analysis

Accepts a multipart/form-data request with a file field containing the PCAP. Saves the file to a temp location, starts the pipeline in a background thread, and immediately returns a job ID.

bashExample request
curl -X POST http://localhost:5001/analyze \
  -F "file=@capture.pcap"
jsonResponse
{ "job_id": "b4cad49f-1a2b-3c4d-5e6f-7890abcdef12" }
GET /stream/:job_id Server-Sent Events progress stream

Opens an SSE stream for the given job. The server sends one event per pipeline step, and a final complete event with the full results payload when analysis finishes.

textEvent format
data: {"event": "step", "data": {"step": 3, "status": "done", "label": "Detection complete", "detail": "2 finding(s)"}}

data: {"event": "complete", "data": {"job_id": "...", "filename": "capture.pcap", "findings": [...], ...}}

data: {"event": "error", "data": {"message": "Failed to parse PCAP: ..."}}
GET /download/:job_id/pdf Download the PDF report

Returns the generated PDF as a file download. Only available after the complete SSE event has been received. Returns 404 if the job doesn't exist or analysis is still running.

GET /download/:job_id/json Download the JSON report

Returns the full analysis report as a JSON file. Contains the same data as the PDF but in machine-readable form — useful for feeding into SIEMs, ticketing systems, or further automation.

Adding a Detection Rule

ForensiQ is designed to be extended. Adding a new detection rule takes about 15 minutes and requires touching exactly two files.

Step 1 — Create the rule file

Create a new file in detection/rules/. Copy this template:

pythondetection/rules/my_rule.py
from typing import List
from core.models import Flow, Finding, Severity, RuleCategory
from detection.rules.base_rule import BaseRule
import config

class MyRule(BaseRule):
    rule_name   = "MY_RULE_NAME"
    description = "One sentence describing what this rule detects."

    def detect(self, flows: List[Flow]) -> List[Finding]:
        findings = []

        for flow in flows:
            # Your detection logic here
            if self._is_suspicious(flow):
                findings.append(Finding(
                    rule_name       = self.rule_name,
                    severity        = Severity.HIGH,
                    category        = RuleCategory.RECONNAISSANCE,
                    title           = f"My Rule: {flow.src_ip} → {flow.dst_ip}",
                    description     = "Describe what was found in plain English.",
                    evidence        = {
                        "src_ip": flow.src_ip,
                        "dst_ip": flow.dst_ip,
                        # Add as many key-value pairs as useful
                    },
                    src_ip          = flow.src_ip,
                    dst_ip          = flow.dst_ip,
                    timestamp       = flow.first_seen,
                    mitre_technique = "T1234",
                    mitre_tactic    = "Tactic Name",
                ))

        return findings

    def _is_suspicious(self, flow: Flow) -> bool:
        # Implement your logic
        return False
⚠️
Never call detect() directly. Always call execute() when invoking a rule — it wraps detect() with error isolation and logging. The engine handles this for you automatically.

Step 2 — Register the rule

Open detection/engine.py and add your rule to the __init__ method:

pythondetection/engine.py
from detection.rules.my_rule import MyRule

class DetectionEngine:
    def __init__(self):
        self.rules = [
            PortScanRule(),
            BruteForceRule(),
            BeaconingRule(),
            ExfiltrationRule(),
            DnsTunnelRule(),
            MyRule(),   # ← add here
        ]

That's it. Your rule will now run on every analysis, its failures will be isolated from other rules, and its findings will appear in both the web UI and the PDF report.

Troubleshooting

0 findings on a real threat PCAP

The most common cause is thresholds being too high. Real malware traffic often involves smaller transfers and less regular timing than the defaults assume. Try lowering EXFIL_BYTES_THRESHOLD to 10 * 1024 and relaxing BEACON_INTERVAL_TOLERANCE to 0.5 in config.py.

VirusTotal returning no scores

Check that your VIRUSTOTAL_API_KEY is set correctly in .env. The free tier allows 4 requests per minute — if you're analyzing a PCAP with many external IPs, the enricher will rate-limit itself and take longer. All results are cached so subsequent analyses of the same IPs are instant.

AI explanations not appearing

ForensiQ requires a GROQ_API_KEY to generate explanations. Get a free key at console.groq.com. If the key is set but explanations still don't appear, check logs/forensiq.log for rate limit errors — the free tier has token-per-minute limits.

Port 5001 already in use

bash
# Find and kill the process using port 5001
lsof -ti:5001 | xargs kill -9

Scapy TLS cipher warnings

Messages like TLS cipher suite not usable. Is the cryptography Python module installed? are harmless warnings from Scapy. They appear when analyzing captures that contain TLS traffic and the cryptography package isn't installed. Install it with pip install cryptography to silence them.

Large PCAP files are slow

ForensiQ is designed to handle multi-GB files, but parsing millions of packets takes time. The MAX_PACKETS config limits processing to 5 million packets by default — any packets beyond that are ignored. Reduce this limit in config.py if you need faster results on large captures.

📋
Check the logs All activity is logged to logs/forensiq.log. Set LOG_LEVEL=DEBUG in your .env file for packet-level detail that makes it easy to trace exactly why a rule did or didn't fire.
